## 0. 一页纸结论

| 问题 | 结论 |
|---|---|
| **能不能做** | 能。标准 B/S Web 系统，手机和电脑读写同一份数据 |
| **为什么不用现成工具** | 只有自建能同时做到"原表无损往返 + 多端一致 + 数据自有" |
| **最大的技术难点** | 不是多端同步，是 Excel 的无损导入导出（见第 5 章） |
| **多久** | **15 人天**（紧凑 12 天，宽松 18 天），不含客户确认等待 |
| **多少钱** | 内网部署 **0 元**；外网穿透 0–600 元/年；纯云约 1000 元/年 |
| **没网怎么办** | 内网服务器覆盖 80% 场景；完全无网用离线补传；蓝牙不建议做主通道 |
| **蓝牙能不能做** | 能做，但**必须原生 App**，+15–25 人天，且传不了照片 |
| **叫什么** | **司南**（备选：信标、墨斗、标点，见第 9 章） |

**三句话读懂方案**

1. 手机和电脑读写同一台服务器上的同一份数据，不存在"同步"这个动作，也就不存在同步失败和版本冲突。
2. Excel 导入时同时保存"原始文本"和"语义值"，导出时优先用原始文本，所以能原样还原。
3. 数据放在内网服务器，外网通过穿透访问同一个服务，**不做双库同步**。

**必须提前和客户对齐的一件事**

> "无损"指**数据、结构、版式**无损，不是文件字节级一致；系统里的照片、评论、操作记录会放在导出文件的附加页签，不破坏原表版式。

## 1. 需求理解

### 1.1 客户原始诉求

> "能否生成手机或电脑均可同步使用的软件，用于项目问题记录和处理、追踪"

拆解为四件事：

| # | 诉求 | 本质 |
|---|---|---|
| 1 | 手机、电脑都能用 | 多端访问，不是两套程序 |
| 2 | 同步使用 | 同一份数据，实时一致，不能各存一份 |
| 3 | 问题记录、处理 | 录入 + 分派 + 状态流转 |
| 4 | 追踪 | 到期提醒、逾期暴露、责任到人、过程留痕 |

补充确认的关键点（本次沟通）：

- 客户要的是**软件**（原话"零件"为笔误），不是在线表格；
- 必须支持**Excel 导入数据库**；
- 必须支持**数据库导出 Excel**；
- 要求**无损跨端**；
- 要求**内网、外网都能用**；
- 希望**没有网络时也能用蓝牙跨端同步**（这条的技术可行性与替代方案见 4.5–4.7）。

### 1.2 真实业务场景

```
现场发现 problem
      │
      ├─ 谁提的？      → 装配/调试/客户/质检
      ├─ 哪台机？      → P7391xxx（31 台）
      ├─ 什么问题？    → 一句话描述，可能带照片
      ├─ 怎么解决？    → 方案 + 责任人
      └─ 什么时候好？  → 计划时间 → 实际完成
                │
                ▼
        方案确定 → 设计下图 → 物料准备 → 装配调试 → 调整线缆后连续运行观察关闭
                │
                ▼
        每周例会过一遍：哪些逾期、哪些卡住、谁在超载
```

关键角色与使用姿势：

| 角色 | 设备 | 场景 | 核心动作 |
|---|---|---|---|
| 调试工程师 | 手机 | 站在机台前 | 拍照、提问题、改状态 |
| 设计/工艺 | 电脑 | 办公室 | 看板筛选、填方案、排期 |
| 项目经理 | 手机 + 电脑 | 例会/出差 | 看逾期、催办、导出周报 |
| 客户/甲方 | 手机 | 现场验收 | 只读查看、提问题（可选） |

### 1.3 成功标准（可验收）

1. 一条问题从提出到关闭，全程可在系统内查到**时间、人、状态变化**；
2. 手机与电脑看到的是**同一条数据**，不存在"同步延迟/版本冲突"；
3. 客户发来的 Excel 能**一键导入**，系统数据能**一键导出**且版式可用于汇报；
4. 逾期问题**自动暴露**，不依赖人翻表；
5. 导入导出往返后，**问题条数、文本、责任人、日期、占位符零丢失**。

## 2. 现状体检：这张 Excel 到底怎么样

### 2.1 表结构

三行表头，两级列组：

```
序号 │ 机台号 │ 存在问题 │ 解决措施 │ 方案确定 │ 设计下图 │ 物料准备 │ 装配调试 │ 完成情况
                                       责任人 计划  责任人 计划  责任人 计划  责任人 计划
```

实质是一张 **"问题 × 四阶段 × (责任人, 计划时间)"** 的矩阵台账。

### 2.2 数据体检结果

用本地解析脚本对虚构演示表做了结构化解析（脚本与原始资料不入库），结果如下。

**规模**

- 有效问题 **36 条**，覆盖 **31 台机**；
- 序号 1–40，**缺 7、19、28、33**（保留原序号，不重排）；
- 25 个责任人/供应商，含 `/` 多人写法。

**填写完整度**（演示种子，统计口径见 `shared/db/seed/issues.seed.json`）

| 阶段 | 有责任人 | 有计划时间 | 说明 |
|---|---|---|---|
| 方案确定 | 33/36 | 33/36 | 5 条进行中，3 条待分派 |
| 设计下图 | 26/36 | 26/36 | 6 条进行中，10 条未开始 |
| 物料准备 | 0/36 | 0/36 | 20 条标 `/`（不适用），16 条空白 |
| 装配调试 | 20/36 | 22/36 | 9 条完成、11 条进行中、2 条 `/` |
| 完成情况 | — | — | 6/36 已闭环，其余待验证或进行中 |

**数据质量问题（演示表刻意保留的脏数据）**

| # | 问题 | 实证 | 影响 |
|---|---|---|---|
| 1 | 阶段台账不完整 | 物料准备 20 条 `/`、16 条空白 | 需要区分“不适用”和“未填写” |
| 2 | 完成情况不全 | 仅 6/36 闭环 | 多数问题还停在过程中，无法只看结果 |
| 3 | 计划时间倒挂 | **5 条**设计下图晚于装配调试 | 排期不可信（如 P7391-018：设计 11.5，装配 11.3） |
| 4 | 时间扎堆 | 11.15 有 13 项、11.3 有 10 项 | 时间是“拍”的不是“排”的，当天不可能完成 |
| 5 | 日期无年份 | `11.1`、`11.5` | 跨月/跨年无法计算逾期 |
| 6 | 文本混入日期列 | 4 处 `已下图` | 程序无法直接解析，必须保留原文 |
| 7 | 机台号疑似笔误 | `P73913118`（多一位） | 统计口径错乱，需人工归组 |
| 8 | 序号缺口 | 缺 7、19、28、33 | 新增/删除无痕迹，不能重排 |
| 9 | 视觉合并未真合并 | 序号/机台号仅首行填写 | 一排序筛选就散架 |
| 10 | 责任人写法不统一 | 含 `/` 多人、空白、角色名混用 | 统计和提醒容易漏人 |

**一个容易忽略的语义细节**

`/` 和空白**不是一回事**：

- `/` = 该阶段**不适用**（如纯软件调试，不需要设计下图）；
- 空白 = **还没填**。

演示数据有 20 条物料准备标 `/`（另有 2 条装配调试标 `/`，合计 22 条不适用）。导入时必须保留这个区分，否则“不需要”会被误判成“未开始”，状态全错。这是“无损”的第一道坎。

**共性问题（平台化机会）**

演示种子按“一机一问题”随机生成，未刻意制造重复标题；真实项目里同一问题常跨多台机重复出现。系统保留 `category` 字段，后续可做问题族/共性标签，让一次改进覆盖多台机，而不是逐台重复排期。

### 2.3 结论

**Excel 是一张"计划台账"，不是一套"追踪系统"。**

它缺的不是字段，而是四样东西：

1. **状态机** —— 没有"当前处于哪一步"的唯一答案；
2. **逾期判定** —— 没有年份、没有实际完成时间，算不出逾期；
3. **变更留痕** —— 谁改了责任人、谁把时间推后，查不到；
4. **闭环压力** —— 完成情况全空，没有任何机制逼着填。

所以客户要软件，不是要一张更漂亮的表。这个判断决定了方案方向。

## 3. 方案调研：四条路

### 3.1 路线对比

| 维度 | A. 在线多维表格<br>（飞书/腾讯文档/WPS） | B. 低代码平台<br>（简道云/宜搭） | C. 自建 Web 系统<br>（推荐） | D. 微信小程序 |
|---|---|---|---|---|
| 上线速度 | 半天 | 1–3 天 | 10–15 天 | 15–20 天 |
| 手机+电脑同步 | ✅ | ✅ | ✅ | ✅ |
| 原表 Excel 无损导入 | ⚠️ 结构会被打平 | ⚠️ 受字段模型限制 | ✅ 可定制 | ✅ 可定制 |
| 导出还原原表版式 | ❌ | ❌ | ✅ | ✅ |
| 阶段矩阵/倒挂校验 | ❌ | ⚠️ 需配置 | ✅ | ✅ |

**免费额度参考**：钉钉宜搭免费版 10 人 / 每月 1000 条；简道云免费版约 30 人；本项目 36 条问题、20 余人，额度都够。但额度不是关键，**导出还原能力**才是。

### 3.2 现成问题追踪软件能不能用

| 产品 | 结论 |
|---|---|
| 禅道 / TAPD / Jira | 字段模型是"需求-任务-缺陷"，没有"四阶段责任人+计划时间"矩阵；Excel 导入导出无法还原原表；手机端是附属品 |
| Redmine | 可定制字段，但定制成本高于自建，界面老旧 |
| 通用工单系统 | 面向售后工单，不支持机台维度的批量问题 |

### 3.3 结论

**自建 B/S Web 系统**是唯一能同时满足"原表无损往返 + 多端一致 + 数据自有"的路线。

代价是 10–15 人天的开发量，但换来的是：

- 客户发来的任何版本 Excel 都能吃进去；
- 导出的表能直接拿去开例会、交甲方；
- 以后换项目、换客户，改个配置就能复用（这是可复制的产品，不是一次性项目）。

> 如果只想先调整线缆后连续运行观察流程，可以先用飞书多维表格跑一周，把字段和状态定义确认下来，再进入开发。不建议长期停留在这条路上，因为导出还原做不到。

### 4.2 为什么这样能"天然同步"

这是整个方案最重要的一句话：

> **手机和电脑不是各自存一份数据再互相同步，而是都读写服务器上的同一份数据。**

- 手机提交 → 写数据库 → 电脑刷新即见；
- 电脑改责任人 → 手机下拉即见；
- 不存在"同步协议"，也就不存在同步失败、版本冲突、合并覆盖。

对比 Excel 的痛点：`P7391_问题台账_演示.xlsx`、`P7391_问题台账_演示(2).xlsx`、微信传来传去，最后谁是最新版没人知道。B/S 架构从根上消灭了这个问题。

**"车间没网"怎么办？** 分三种情况处理（详见 4.4–4.7）：

- 只有内网、没有外网 → 车间服务器 + WiFi，这是最常见的情况；
- 完全没有任何网络 → 本地离线库 + 联网自动补传（V1.1）；
- 完全无网且要多台设备当场对账 → 二维码/文件交换（V1.2），蓝牙是下策。

### 4.3 跨端一致性设计

| 层面 | 做法 |
|---|---|
| 数据 | 单一数据库，单一 API，无本地副本 |
| 布局 | ≥1024px 表格视图；<768px 卡片视图；同字段、同数据 |
| 字段 | 手机卡片只显示 6 个关键字段，详情页看全量，不做字段裁剪 |
| 并发 | 每条记录带 `version`，提交时比对，冲突提示"该条已被 XX 修改，请刷新" |
| 实时 | 默认 30 秒轮询；需要时上用 SignalR 推送 |
| 时区/编码 | 统一 UTC 存储、本地时区显示；全链路 UTF-8 |
| 附件 | 手机拍照直传，服务端压缩出缩略图，原图保留 |
| 导出 | 同一套模板与数据，手机端导出 PDF/Excel 均可 |

**两个必须提前知道的坑：**

1. **PWA 的"添加到主屏幕"需要 HTTPS**。纯内网 HTTP 环境下 Service Worker 不可用，离线缓存也就没有。要么内网配自签证书，要么放弃离线能力。
2. **微信内置浏览器**可以正常打开系统，但 iOS 微信里不能"添加到主屏幕"，需要提示用户"用系统浏览器打开"。安卓微信可以。

### 4.4 三种网络环境，一套系统

工厂的现实不是"有网 / 没网"二选一，而是三种：

| 环境 | 典型场景 | 方案 | 体验 |
|---|---|---|---|
| **A. 有外网** | 办公室、出差、家里 | 云端或内网穿透，随时访问 | 最好 |
| **B. 只有内网** | 车间有 WiFi，但没接外网 | 车间服务器，手机连同一 WiFi | 好 |
| **C. 完全没有网络** | 新厂房、地下室、临时工位 | 本地离线库，回到有网环境自动补传 | 可用，但有延迟 |

决策树：

```
现场有没有网络？
│
├─ 有外网 ──────────► 云服务器 或 内网+穿透（推荐后者）
│
├─ 没外网，但有 WiFi ─► 车间服务器 + 手机连同一 WiFi
│                      （这是制造业最常见的情况）
│
└─ 完全没有任何网络
   │
   ├─ 单人记录、回办公室汇总 ──► 离线本地库 + 联网补传
   │
   └─ 多台手机当场对账 ──────► 二维码/文件交换（见 4.6）
                              蓝牙是下策（见 4.5）
```

**部署形态对比**

| 形态 | 数据在哪 | 手机怎么连 | 成本 | 适合 |
|---|---|---|---|---|
| 纯云 | 云服务器 | 4G / WiFi | ~1000 元/年 + 域名备案 | 客户经常出差、要远程看 |
| **内网为主 + 穿透（推荐）** | 车间服务器 | WiFi；外网走穿透 | 0–200 元/年 | 数据在自己手里，内外网都能用 |
| 纯内网 | 车间服务器 | 只能同一 WiFi | 0 | 数据绝不出厂，但出差看不了 |
| 双部署 + 双向同步 | 两边各一份 | 就近访问 | 高（+8 人天） | 内外网物理隔离，且都要写 |

> **关键判断**：你要"内网、外网都支持"，不等于要"两套数据库"。
> 最经济的做法是**内网一台服务器做唯一主库，公网通过 frp / Cloudflare Tunnel 映射到同一个服务**。一套数据、两个入口，不存在双库同步和冲突。
> 只有客户内网物理隔离（网闸）时，才需要双部署，那时再单独评估。

### 4.5 蓝牙：能做，但不是你想的那样

先把结论摆在前面：

| 你的期望 | 能否实现 | 说明 |
|---|---|---|
| 手机浏览器通过蓝牙同步数据 | ❌ **浏览器内做不到** | Safari 全版本不支持 Web Bluetooth，2026 年 4 月仍无支持计划 |
| 安卓手机浏览器蓝牙同步 | ⚠️ 只能连外设 | Chrome 支持，但浏览器只能当"主设备"，不能当"蓝牙服务器" |
| 两台手机蓝牙互传问题数据 | ✅ 需要原生 App | 浏览器做不到，必须 Flutter / MAUI / 原生开发 |
| 蓝牙传照片 | ❌ 不现实 | 实测 10–50 KB/s，一张 3 MB 照片要 1–5 分钟 |
| 蓝牙传文本数据 | ✅ 可以 | 36 条约 10 KB（压缩后），几秒钟 |
| 蓝牙多人实时同步 | ❌ 不适合 | 无标准同步协议，配对/后台/兼容性都是坑 |

**技术事实（已核实）**

1. **Web Bluetooth 兼容性**：Chrome、Edge、Opera、Samsung Internet 支持；**Safari（macOS / iOS / iPadOS）全版本不支持**，Firefox 也不支持。iOS 上要靠 `iOSWebBLE` 这类 Safari 扩展做 polyfill，普通工人不可能去装扩展。
2. **浏览器只能做 Central**：网页可以扫描并连接"蓝牙外设"，但没法让手机变成"蓝牙外设"等着别人连。所以"手机 A 开网页、手机 B 连它"这条路走不通。
3. **实际速率**：BLE 4.2 理论 100 KB/s，实测 iPhone 约 **12 KB/s**；BLE 5 理论更高，但手机间协商后通常也就几十 KB/s。传文本够用，传图片不够。
4. **没有现成的同步协议**：蓝牙只提供"字节管道"，增量同步、断点续传、冲突检测都得自己实现。

**如果坚持要蓝牙，代价是什么**

| 项 | 代价 |
|---|---|
| 必须做原生 App（放弃纯 Web） | Flutter 或 .NET MAUI，iOS/Android 双端 |
| 开发量 | **+15–25 人天**，且要真机兼容性测试 |
| 维护 | 每次 iOS/Android 大版本升级都要回归 |
| 现场支持 | 配对失败、权限被拒、后台被杀，远程很难排查 |
| 功能天花板 | 只能同步文本，照片仍要等有网 |

**结论**：蓝牙适合"连扫码枪、蓝牙打印机、传感器"这类外设，**不适合作为问题数据的同步主通道**。

### 4.6 "完全无网"的务实方案：二维码 / 文件，而不是蓝牙

如果目标只是"现场记录不丢，能带回办公室"，二维码比蓝牙更靠谱：

| 维度 | 蓝牙 | 二维码 | 文件导出 |
|---|---|---|---|
| 跨平台 | iOS 必须原生 App | ✅ 全平台 | ✅ 全平台 |
| 安装 | 要装 App | ✅ 不用 | ✅ 不用 |
| 权限 | 配对 + 定位 + 后台 | 相机 | 文件 |
| 速率 | 10–50 KB/s | ~1–2 KB/张，10 KB 约 6–8 张 | 秒级 |
| 照片 | ❌ | ❌ | ✅ U 盘/微信 |
| 实现成本 | 高 | 低（+2 人天） | 低 |
| 适合 | 设备互联 | 小数据量对账 | 大批量汇总 |

**二维码交换怎么用**

```
手机 A：选择要分享的变更 → 生成 6–8 张二维码（分片 + 校验码）
手机 B：依次扫码 → 自动拼包 → 校验 → 合并入库
```

- 数据包：JSON → gzip → Base64 → 分片，每片带序号和 CRC；
- 36 条问题的增量通常 <10 KB，扫 6–8 张即可；
- 零安装、跨平台、不需要网络和配对；
- 缺点：照片传不了，操作比蓝牙繁琐一点，但比"装 App 配蓝牙"现实得多。

**文件交换（大批量场景）**

- 一键导出 `.db` 或 `.json` 加密包；
- 微信 / U 盘 / 数据线传到另一台设备；
- 另一台导入合并，适合"现场记一周，回办公室汇总"。

### 4.7 离线优先架构（要做真离线时的正确做法）

如果最终决定支持"完全无网操作"，架构要从"在线"改成"离线优先"：

**核心原则**：所有操作先写本地，界面立即响应；有网时后台补传。不是"没网了就报错"。

**同步模型**

| 元素 | 设计 |
|---|---|
| 记录 ID | 客户端生成 UUID，不依赖服务端自增 |
| 版本 | 每条记录 `version` + `updated_at` + `device_id` |
| 本地日志 | `oplog` 记录每一次增删改，按序重放 |
| 增量拉取 | 服务端维护 `cursor`，客户端只拉"上次之后"的变更 |
| 冲突判定 | 同一字段两端都改 → 冲突 |
| 冲突解决 | 默认字段级 LWW（最后写入胜出）；关键字段（责任人、状态、关闭）弹人工仲裁 |
| 照片 | 先存本地，联网后后台补传，带失败重试 |
| 传输层 | 网络、内网、蓝牙、二维码都只是"搬字节"的通道，业务逻辑不变 |

**这个抽象很重要**：同步协议只写一次，以后加蓝牙通道只是加一个"运输驱动"，不用重写业务。

**离线能力的代价**

| 能力 | 增量工作量 |
|---|---|
| 基线（纯在线） | — |
| + 本地离线库与补传 | **+5 人天** |
| + 二维码数据交换 | **+2 人天** |
| + 内外网双部署双向同步 | +8 人天（不推荐，优先用穿透） |
| + 蓝牙原生伴侣 App | **+15–25 人天**（单独立项评估） |

**建议的取舍**：

- **MVP 做**：在线 + 内网 + 穿透（覆盖 90% 场景）；
- **V1.1 做**：离线本地库 + 自动补传（覆盖车间断网）；
- **V1.2 按需做**：二维码交换（覆盖完全无网的对账）；
- **蓝牙**：除非客户明确要求"连蓝牙外设"（扫码枪/打印机），否则不做。

## 5. Excel 双向通道：导入、导出与往返无损

> 这一章是方案的核心。客户的工作流就是"发 Excel"，如果这一步做不好，系统一定被弃用。

### 5.1 先定义什么叫"无损"

"无损"必须分层，否则永远扯不清。建议按五层定义，写进验收标准：

| 层级 | 内容 | 能否做到 | 实现方式 |
|---|---|---|---|
| **L0 字节级** | 原文件一个字节都不变 | ✅ | 导入时归档原文件，随时下载 |
| **L1 数据级** | 每个单元格的文本、空值、`/` 占位符、行序、行号 | ✅ | 双字段存储（见 5.2） |
| **L2 结构级** | 三行表头、两级列组、列顺序、列宽、冻结窗格、合并 | ✅ | 模板化导出 + NPOI |
| **L3 样式级** | 字体、边框、底色、对齐、数字格式 | ✅ 95% | 从原表读取样式参数套用 |
| **L4 语义级** | 日期是真日期、责任人是真人员、状态可计算 | ✅ | 结构化字段 + 原始文本并存 |

**做不到的**：把用户在系统里新增的字段、图片、评论"塞回"原表版式而不改变结构。这部分通过"附加列/附件页"解决，并在导入时就说明。

一句话对齐客户：

> 导出文件和原表**看起来一样、数据一样、能直接开会用**；但系统里多出来的照片、评论、操作记录，会放在额外的页签里，不破坏原表版式。

### 5.2 核心技术手段：双字段存储

每个"可能被人工改写"的字段，同时存两份：

```sql
due_date   DATE          NULL,   -- 语义值：2026-11-05，用于逾期计算、排序
due_raw    NVARCHAR(32)  NULL,   -- 原文："11.5" / "已下图" / "/" / ""
```

| 场景 | 取值规则 |
|---|---|
| 导入 | `due_raw` 原样保存；能解析则同时写 `due_date` |
| 系统内编辑 | 同时更新两者（`due_raw` 格式化为 `11.5`） |
| 导出 | 优先 `due_raw`，为空才用 `due_date` 格式化 |
| 统计/提醒 | 只用 `due_date`，`/` 和 `已下图` 不参与计算 |

责任人同理：

```sql
owner_text  NVARCHAR(64)   -- 原文："王工/赵工"
owner_ids   NVARCHAR(128)  -- 关联人员表："3,7"，用于指派和统计
```

**这是能做到"往返无损"的根本原因**：语义字段负责算，原始字段负责还原。

### 5.3 导入管线（8 步）

```
① 上传            ② 指纹去重         ③ 格式识别        ④ 表头探测
   .xls/.xlsx        SHA-256             BIFF8/OOXML       自动找表头行
                                                                  │
⑧ 入库+归档       ⑦ 冲突处理         ⑥ 校验            ⑤ 列映射
   事务写入          新增/更新/跳过      必填/日期/规则     自动+手动修正
   原件存档          字段级 diff        错误行高亮        保存为模板
   导入报告                                             下次一键复用
```

#### ① 上传

- 支持 `.xls`（BIFF8）和 `.xlsx`（OOXML），单文件 ≤ 20 MB；
- 拖拽或选择，手机端也能传（微信传文件 → 用浏览器打开系统上传）。

#### ② 指纹去重

- 计算文件 SHA-256，若与历史导入完全相同，提示"该文件已于 X 月 X 日导入过，是否继续？"；
- 避免客户重复发同一份文件导致重复数据。

#### ③ 格式识别

- 按文件头魔数判断真实格式，不信任扩展名（常见坑：`.xls` 实际是 HTML 或 CSV）；
- `.xls` 用 NPOI HSSF 读取；`.xlsx` 用 XSSF；
- 加密文件给出明确提示。

#### ④ 表头探测

原表是 3 行表头 + 两级列组。不能写死，做法：

1. 从上往下扫描，找"非空单元格最多且下一行含关键字（责任人/计划/时间）"的行；
2. 识别两级列组：上行是组名（方案确定/设计下图/物料准备/装配调试），下行是子列（责任人/计划时间）；
3. 结果展示给用户确认，允许手动调整"表头占几行、数据从第几行开始"。

这样客户下次改成 2 行表头、或者加了"备注"列，也不用改代码。

#### ⑤ 列映射

- 内置同义词表：`存在问题` ≈ `问题描述` ≈ `问题点`；`机台号` ≈ `设备号` ≈ `机台`；
- 自动匹配 + 手动拖拽修正；
- 保存为**导入方案**（按项目/按客户），下次同格式文件一键套用。

#### ⑥ 校验

分级处理，不搞"一刀切拒绝"：

| 级别 | 规则 | 处理 |
|---|---|---|
| 错误 | 机台号为空、问题描述为空 | 该行不导入，报告中列出 |
| 警告 | 机台号不符合 `P7391\d{3}(-\d)?`、日期无法解析、设计晚于装配 | 允许导入，标黄提示 |
| 提示 | 与现有问题重复、序号缺口 | 提示，人工决定 |

#### ⑦ 冲突处理（增量导入的关键）

客户会反复发新版 Excel（`- 副本`、`- 副本(2)`），所以导入必须支持**增量合并**，不是每次清空重来。

业务主键建议：`项目 + 机台号 + 问题标题`（可人工指定）。

预览界面明确告诉用户：

```
本次导入预览
  新增   3 条
  更新  12 条   ← 可展开看字段级 diff
  无变化 42 条
  冲突   2 条   ← 系统内已改，Excel 也改了
```

三种策略：

| 策略 | 适用 |
|---|---|
| 仅新增 | 首次导入，或只关心新问题 |
| 增量合并（推荐） | 日常更新，Excel 为准或系统为准可选 |
| 全量覆盖 | 以 Excel 为唯一真相，系统内修改会被覆盖（需二次确认） |

**冲突那一档必须有**：系统里有人把时间从 11.5 改到 11.20，Excel 里还是 11.5，直接覆盖就把人的工作冲掉了。

#### ⑧ 入库 + 归档 + 报告

- 单事务写入，失败整体回滚；
- 生成 `import_batch` 记录：文件哈希、行数、操作人、时间、策略；
- **原文件存入 `source/` 归档**，随时可下载（这就是 L0 无损）；
- 输出导入报告：成功 N 条、跳过 M 条、警告 K 条，附行号，可导出。

**支持按批次回滚**：误导入一键撤销（按 batch_id 反向操作）。

### 5.4 解析难点清单（本项目实测）

| # | 难点 | 实测情况 | 对策 |
|---|---|---|---|
| 1 | 三行表头 + 两级列组 | 是 | 表头探测 + 用户确认 |
| 2 | 视觉合并（非真合并） | xlrd 读到 0 个合并区域，序号/机台号只在首行 | 按序号分组向下填充；导出时同样只在首行写 |
| 3 | 序号缺口 | 缺 7 / 19 / 28 / 33 | 保留原序号，另生成内部 ID，不重排 |
| 4 | 机台号笔误 | `P73913118` 多一位 | 警告不拦，人工确认后改正 |
| 5 | 日期无年份 | `11.1` | 导入向导指定基准年份；从文件名提取（20261123 → 2026） |
| 6 | 文本混入日期列 | 4 处 `已下图` | 存 `due_raw`，`due_date` 留空，不算逾期 |
| 7 | `/` 与空白语义不同 | 22 条 `/` | `/` 存为"不适用"，空白存为"未填"，状态机区分 |
| 8 | 责任人多人 | `王工/赵工` | 拆分为人员关联，原文保留 |
| 9 | 机台号带后缀 | `P7391306-1/-2` | 允许 `-\d` 后缀 |
| 10 | 编码/全角符号 | 中文标点、全角斜杠 | 统一 NFKC 归一化后再匹配，原文照存 |

### 5.5 增量同步：把"发 Excel"变成正式工作流

这是本系统相对通用工具的**差异化能力**：

```
客户/项目经理 每周发来 Excel
        │
        ▼
  上传 → 自动识别 → 变更预览（新增/更新/冲突）
        │
        ├─ 确认 → 入库 → 生成变更摘要（可直接发群）
        │
        └─ 取消 → 不改动任何数据
```

配套"变更摘要"文本，可直接复制到微信群：

```
P7391 问题清单更新（11-23）
新增 3 条｜关闭 5 条｜逾期 2 条
逾期：P7391106 接近开关信号偶发丢失（王工，超 6 天）
```

### 5.6 导出管线

```
① 选范围        ② 选模板          ③ 取数            ④ 渲染
   全部/筛选/选中   原表版式/标准/汇报   双字段优先 raw      NPOI 写单元格
                                                          套列宽/合并/边框/字体
        │
        ▼
⑤ 附加页（可选）  ⑥ 校验            ⑦ 下载
   附件清单/变更记录  条数/日期/文本比对   .xlsx（默认）
                                        .xls（兼容，可选）
```

**模板设计**

| 模板 | 用途 | 特点 |
|---|---|---|
| 原表版式 | 交回客户、对照原表 | 三行表头、列组、列宽、冻结窗格完全复刻 |
| 标准版 | 内部周会 | 一条一行、扁平列、含状态/逾期天数 |
| 汇报版 | 给领导/甲方 | 按机台汇总 + 阶段完成率 + 逾期 TOP |

**导出时必须注意的细节**

1. **日期回写**：优先 `due_raw`，保证 `11.5` 还是 `11.5`，不会被格式化成 `2026-11-05`；
2. **`/` 保留**：不适用阶段导出为 `/`，不能变成空白；
3. **视觉合并还原**：同一序号组只在首行写序号和机台号，其余留空（与原表一致）；
4. **列宽**：从原表读取并套用，否则中文列会挤成一坨；
5. **冻结窗格**：冻结前 3 行 + 前 4 列，方便横向查看；
6. **数字格式**：机台号是文本，不能变成科学计数法（`P7391101` 不会被转）；
7. **超链接**：附件以超链接形式放在"附件"列，指向系统内地址；
8. **导出说明页**：导出时间、筛选条件、条数、导出人，避免"这版是哪天的"扯皮。

**为什么默认导出 `.xlsx` 而不是 `.xls`**

- `.xls`（BIFF8）是 2003 格式，单表上限 65536 行、样式能力弱；
- 写 `.xls` 的库（xlwt）已停止维护；
- 现代 Excel/WPS/手机 Office 全部支持 `.xlsx`；
- 若客户老系统只认 `.xls`，用 NPOI HSSF 单独输出，作为兼容选项。

### 5.7 往返一致性验收（Round-trip Test）

这是把"无损"变成可验收动作的关键：

```
原表.xls ──导入──> 数据库 ──导出──> 导出.xlsx ──再导入──> 数据库'
                                                          │
                                                    逐字段比对
```

断言清单：

| # | 断言 | 判定 |
|---|---|---|
| 1 | 问题条数一致 | 36 = 36 |
| 2 | 每行问题文本、措施文本完全一致 | 字符串逐字比对 |
| 3 | 责任人原文一致（含 `/`、多人） | 逐字比对 |
| 4 | 日期原文一致（`11.5` 不变成 `11/5/2026`） | 逐字比对 |
| 5 | `/` 与空白不混淆 | 计数比对 |
| 6 | 机台号、序号一致 | 逐字比对 |
| 7 | 行顺序一致 | 按 source_row 比对 |
| 8 | 已知脏数据（`已下图`、`P73913118`）原样保留 | 白名单校验 |

**建议把这份清单直接写进验收标准**，跑通才算交付。脚本可自动化，每次改动后回归。

### 5.8 兜底策略

再好的解析也可能遇到"客户发来一个完全变态的表"。所以永远保留一条退路：

- 原始文件**永久归档**，随时下载；
- 任何一条问题都能追溯到"来自哪个文件、第几行"；
- 导出失败时，至少能导出"标准版"CSV，数据不丢。

## 6. 数据模型草案

```sql
-- 项目
projects(id, code, name, customer, status, created_at)

-- 机台
machines(id, project_id, code, name, seq_no, status)
--   code: P7391101 ... P7391315（唯一约束 project_id + code）

-- 问题（主表）
issues(
  id, project_id, machine_id,
  seq_no,              -- 原表序号（可为空，不重排）
  title,               -- 存在问题
  solution,            -- 解决措施
  status,              -- 待分派/方案中/设计中/备料中/装配中/待验证/已关闭/已取消
  priority,            -- 高/中/低（原表没有，新增）
  category,            -- 问题族标签，用于共性统计
  completion_text,     -- 完成情况原文
  closed_at,           -- 实际关闭时间
  source_batch_id,     -- 来自哪次导入
  source_row,          -- 原表行号
  version,             -- 乐观锁
  created_at, updated_at
)

-- 四阶段进度（一条问题 4 行）
issue_stages(
  id, issue_id, stage_code,       -- plan/design/material/assembly
  owner_text, owner_ids,          -- 原文 + 关联
  due_date, due_raw,              -- 语义 + 原文
  state,                          -- na/not_started/in_progress/done/overdue
  actual_date, remark
)

-- 人员
users(id, name, role, dept, phone, active)
--   active=0 停用不删除，保证历史可追溯

-- 附件
attachments(id, issue_id, file_name, stored_path, thumb_path, size, mime, uploaded_by, created_at)

-- 评论/时间线
comments(id, issue_id, user_id, content, created_at)

-- 变更审计（字段级）
activity_log(id, entity, entity_id, field, old_value, new_value, user_id, created_at)

-- 导入批次
import_batches(id, project_id, file_name, file_hash, strategy, total, inserted, updated, skipped, created_by, created_at)

-- 导出模板
export_templates(id, project_id, name, config_json)
```

**几个设计决策的理由**

| 决策 | 理由 |
|---|---|
| 阶段单独建表，不塞进 issues | 阶段可扩展（以后加"验收"）、可单独查逾期、可保留每阶段历史 |
| `due_raw` 与 `due_date` 并存 | 无损往返的核心，见 5.2 |
| `seq_no` 不重排 | 重排会丢失与原表的对应关系，追溯就断了 |
| `source_row` 保留 | 出问题能定位到原表第几行 |
| `version` 乐观锁 | 手机和电脑同时改，能发现冲突 |
| `active` 停用而非删除人员 | 历史记录里的人名不能变成"未知" |
| 全量审计 | 客户问"谁把时间改了"，能答上来 |

## 8. 技术选型

### 8.1 推荐栈（方案 A）

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | **.NET 8 / ASP.NET Core** | 你现有技术栈是 C#/WinForms，后续自己能维护；Windows 部署最顺 |
| Web | **Razor Pages + htmx** | 无前端构建链，服务端渲染，弱网友好；比 Blazor Server 更适合车间网络 |
| UI | **Tailwind CSS** | 响应式快，手机/电脑一套代码 |
| 数据库 | **SQLite（WAL 模式）** | 单文件、易备份、零运维；10 万条以内无压力；需要时换 SQL Server 只改 provider |
| ORM | **EF Core** | 迁移、审计拦截器都成熟 |
| Excel | **NPOI** | 唯一同时读写 `.xls` 和 `.xlsx` 的成熟 .NET 库，样式/合并/列宽都支持 |
| 认证 | Cookie + ASP.NET Core Identity（简化版） | 内网系统不需要 OAuth |
| 定时任务 | `BackgroundService` | 每日扫描逾期、发提醒、备份 |
| 部署 | Kestrel + Windows 服务（NSSM） | 开机自启，无需 IIS |
| 日志 | Serilog + 文件滚动 | 出问题能查 |

### 8.2 备选栈（方案 B）

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | FastAPI | 开发快，脚本化强 |
| 前端 | Jinja2 + htmx | 同 A |
| 数据库 | SQLite | 同 A |
| Excel 读 | xlrd（.xls）、openpyxl（.xlsx） | 成熟 |
| Excel 写 | openpyxl | **只能写 .xlsx，不能写 .xls** ← 关键短板 |
| 部署 | uvicorn + Windows 计划任务 | 可行但不如 A 稳 |

> 如果客户明确要求导出 `.xls`，Python 方案需要额外装 LibreOffice 做格式转换，不如直接选 A。

### 8.3 部署方案：内网 + 外网双入口

**推荐拓扑**（一套数据，两个入口）：

```
        ┌──────────────────────────────┐
        │  公网入口（可选）              │
        │  https://p2625.xxx.com        │
        │  └─ frp / Cloudflare Tunnel   │
        └──────────────┬───────────────┘
                       │ 映射
        ┌──────────────▼───────────────┐
        │  车间服务器（Windows）         │
        │  唯一主库 SQLite + uploads    │
        │  内网地址 http://192.168.x.x  │
        └──────────────┬───────────────┘
                       │ 局域网 WiFi
        ┌──────────────┼───────────────┐
        │              │               │
     手机/平板       办公室电脑       车间大屏
```

| 场景 | 方案 | 成本 | 说明 |
|---|---|---|---|
| **内网访问（必做）** | 车间一台 Windows 跑服务，手机连同一 WiFi | 0 元 | 主路径，断外网也能用 |
| **外网访问（推荐）** | 内网服务器 + frp 穿透 | 轻量云 1C1G ≈ 300–600 元/年 | 需要一台有公网 IP 的小服务器做跳板 |
| **外网访问（零成本）** | Cloudflare Tunnel | 0 元 | 不用公网 IP，国内速度一般，适合低频查看 |
| **外网访问（最简）** | 花生壳/贝锐等内网穿透 | 免费版限流量 | 上手快，长期用建议付费版 |
| 纯云部署 | 云服务器 1C2G + 域名 | ~1000 元/年 + 备案 | 只有客户完全没有内网机器时才选 |

**穿透工具对比**

| 工具 | 需要公网 IP | 国内速度 | 成本 | 适合 |
|---|---|---|---|---|
| frp（自建） | 需要一台跳板机 | 好 | 跳板机费用 | 长期稳定使用 |
| Cloudflare Tunnel | 不需要 | 一般 | 0 | 临时/低频 |
| 花生壳 | 不需要 | 较好 | 免费限流 | 快速调整线缆后连续运行观察 |
| Tailscale / ZeroTier | 不需要 | 一般 | 0 | 团队内部，不适合给客户扫码 |

**公网入口必须做的安全措施**

1. 强制 HTTPS（穿透隧道或反向代理配证书）；
2. 关闭数据库端口对外，只暴露 Web 端口；
3. 登录失败 5 次锁定 10 分钟；
4. 客户/访客账号只读，且可设置有效期；
5. 所有导出、删除操作记审计日志；
6. 每日备份，且备份文件不在 Web 目录下。

**建议的推进顺序**

1. 先内网跑通（0 成本，调整线缆后连续运行观察流程）；
2. 客户认可后，加 Cloudflare Tunnel 或 frp 开外网；
3. 不要一上来买云服务器——数据在车间，响应更快，也不受公网波动影响。

### 8.4 备份与迁移

- SQLite 每日自动备份到 `backup/YYYYMMDD.db`，保留 30 天；
- 附件目录同步备份（可用 robocopy 到 NAS/网盘）；
- 一键导出全量数据（ZIP：数据库 + 附件 + Excel）；
- 迁移到新机器：拷贝目录 + 改配置，5 分钟完成。

## 9. 项目命名建议

### 9.1 命名逻辑

这个软件的本质是：**让每一条现场问题都有方向、有回响、有句号**。

上一版「盯办」被否掉是对的——它是功能直译，像内部工具，没有品牌感。好名字应该满足：

1. **有意象**：能画出来，能做 logo，不是功能的同义词；
2. **两个字**：手机图标下显示完整，念着有节奏；
3. **有出处**：要么来自工艺/工具，要么来自文化符号，经得起问"为什么叫这个"；
4. **能脱离 P7391 复用**：以后 P2626、售后、质量体系都能装进去；
5. **拼音干净**：能做仓库名、域名、小程序名。

### 9.2 主推：**司南**（Sinan / Compass）

> **让每个问题，都有方向。**

| 项 | 内容 |
|---|---|
| 中文名 | 司南 |
| 英文/仓库名 | `sinan` / 对外 `Compass` |
| 意象 | 中国古代指南器：铜盘上放一把磁勺，静止时勺柄指南 |
| 副标题 | 设备安装调试问题闭环系统 |
| Slogan | 让每个问题，都有方向 |
| 对外正式名 | 司南 · P7391 安装调试问题闭环管理系统 |

**为什么是它**

- **"司"是执掌，"南"是方向**——问题管理最怕的就是"跑偏、漏项、没人管"，司南管的就是方向；
- 和"安装调试"的现场语言天然契合：找正、对中、定向，都是"司南"的语义场；
- 中国四大发明级的文化符号，给制造业客户汇报时有分量，不轻浮，也不土；
- 两个字，图标好做：**磁勺 + 刻度盘**，极简线条就能识别；
- 可扩展成产品族：司南·P7391、司南·售后、司南·质量。

**视觉方向**

- Logo：俯视铜盘 + 一把指向南方的勺，单色线条；或只取"勺柄 + 刻度"的抽象形；
- 主色：**青铜绿**（#3F5D53）+ 铜色（#B08D36）点缀，工业且有质感；
- 动效：勺柄旋转 → 停住 → 指向"已关闭"，适合做启动页。

**风险提示**：市场上有"司南导航"等同名企业，**对外商用前需在中国商标网查重**；内部项目名/仓库名不受影响。

### 9.3 备选（按客户气质选）

| 名字 | 意象 | 寓意 | 视觉方向 | 最适合 |
|---|---|---|---|---|
| **信标**<br>Beacon | 灯塔 / 无线电信标 | 每个问题都是一个信号，被接收、被响应、被关闭 | 同心圆波纹 + 一个亮点；深海蓝 + 信号橙 | 新能源、3C、年轻团队 |
| **墨斗**<br>Inkline | 木工弹线工具 | 墨线一弹，歪的留下直痕——取直、校准、立规矩 | 墨斗轮廓 + 一道直线；墨黑 + 朱红 | 传统机械、模具、重工 |
| **标点**<br>Period | 句号 | 给每条问题画上句号；有始有终 | 放大的句号 + 清单线条；黑白 + 一点红 | 设计驱动型客户、汇报型场景 |
| **啄木**<br>Woodpecker | 啄木鸟 | 问题藏在里面，一条条啄出来 | 鸟喙 + 年轮；木色 + 松绿 | 需要亲和力、要做吉祥物的场景 |

**四个名字的气质差异**

```
司南  ── 文化底蕴 + 工业感     （稳，适合国企/大型制造）
信标  ── 现代 + 科技感         （快，适合新能源/3C）
墨斗  ── 匠人 + 工艺感         （实，适合传统机械）
标点  ── 极简 + 文艺感         （轻，适合设计型团队）
```

### 9.4 命名自检清单（定名前必做）

| # | 检查项 | 说明 |
|---|---|---|
| 1 | 商标查重 | 中国商标网查第 9 类（软件）、第 42 类（技术服务） |
| 2 | 域名可用 | `.com` / `.cn` 是否被占 |
| 3 | 公众号/小程序名 | 微信公众平台搜是否重名 |
| 4 | 拼音歧义 | 是否有不雅谐音（各地方言） |
| 5 | 英文撞名 | GitHub、Product Hunt 是否有同名知名项目 |
| 6 | 客户接受度 | 把 3 个候选发给客户，让他们选——比我们自己纠结有效 |

### 9.5 不建议

- 「盯办」「销号」「归零」—— 功能直译或行业黑话，准确但没有品牌感；
- 「问题管理系统」「问题追踪平台」—— 正确但无辨识度，做不成产品；
- 「P7391 问题表」—— 绑死单个项目，下个项目要重做；
- 英文名如 IssueTracker / BugFlow —— 太通用，搜不到，也不符合国内客户语境。

| P3 Excel 导入 | 解析、映射、预览、校验、批次、回滚 | 原表能导进来 | 2.5 天 |
| P4 Excel 导出 | 三套模板、样式复刻、往返校验 | 导出能开会用 | 2 天 |
| P5 移动端 | 响应式、卡片视图、拍照 | 手机能用 | 1.5 天 |
| P6 提醒报表 | 逾期扫描、通知、基础统计 | 能催办 | 1 天 |
| P7 联调验收 | 往返测试、修 bug、培训、文档 | 交付 | 2 天 |
| **合计** | | | **15 人天** |

紧凑可压到 12 天，宽松 18 天（不含客户确认等待、不含需求蔓延）。

**可选模块（按需追加，不进 MVP）**

| 模块 | 增量 | 触发条件 |
|---|---|---|
| 外网穿透部署（frp/CF Tunnel + HTTPS） | +0.5 天 | 客户要在家里/出差看 |
| 离线本地库 + 自动补传 | +5 天 | 车间经常断网 |
| 二维码分片数据交换 | +2 天 | 完全无网且要多机对账 |
| 蓝牙伴侣 App（原生） | +15–25 天 | 客户明确要求手机间蓝牙，或要连蓝牙外设 |
| 内外网双部署双向同步 | +8 天 | 内网物理隔离，且有网闸 |

> 一个务实的判断：**80% 的"工厂没网"其实是"没外网"，局域网 WiFi 是有的**。
> 先按"内网服务器 + 可选穿透"设计，真遇到完全无网的工位，再用离线补传覆盖。蓝牙留到最后评估，不要一上来就为它做原生 App。

### 10.2 建议的推进方式

1. **先做 P0 + P3/P4 的 Excel 通道原型**（约 3 天），拿真实表跑一遍导入导出，让客户看到"原表能进能出"。这是最能建立信任的一步。
2. 再补问题管理界面和移动端。
3. 最后做提醒和报表。

> 不要先做漂亮的看板。这个项目的成败在 Excel 通道，先把它跑通。

## 11. 风险与对策

| # | 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|---|
| 1 | 客户对"无损"期望是字节级 | 高 | 验收扯皮 | 用第 5.1 节五层模型提前对齐，写进验收 |
| 2 | `.xls` 老格式样式还原不完美 | 中 | 观感差异 | 默认导 `.xlsx`，样式做到 95%，结构 100% |
| 3 | 工厂无网/弱网 | 中 | 手机用不了 | 内网部署 + 手机连 WiFi；V1.1 离线补传；完全无网用二维码/文件 |
| 3b | **客户以为"浏览器就能蓝牙"** | **高** | 期望落空 | 用 4.5 的技术事实对齐：iPhone 不支持 Web Bluetooth，要做必须原生 App |
| 3c | 为蓝牙上原生 App，成本失控 | 中 | +15–25 人天 | 先确认是否必须"手机间直传"，优先用二维码替代 |
| 3d | 内外网双部署导致数据分叉 | 中 | 两套数据不一致 | 优先"内网单库 + 穿透"，不做双写 |
| 4 | 客户不填完成情况（原表 0/36 就是证据） | **高** | 系统变空壳 | 状态推进做成"必须点一下"；到期自动提醒；周报自动生成 |
| 5 | 责任人变动/离职 | 中 | 历史数据乱 | 人员停用不删除；责任人可转移 |
| 6 | 需求蔓延（要审批流、要 MES 对接） | 高 | 工期失控 | MVP 锁定清单，超出走 V1.1 |
| 7 | 手机浏览器兼容 | 低 | 个别机型异常 | 优先适配微信内置浏览器 + Chrome/Edge |
| 8 | 数据量增长 | 低 | 性能 | SQLite 10 万条无压力，预留 PostgreSQL 迁移路径 |

**第 4 条要特别说**：原表完成情况 0/36，说明"让人填表"这件事本身就失败了。新系统不能只是"更好看的表"，必须做到：

- 改状态只需 1 次点击（不要弹窗填表）；
- 逾期自动出现在"我的待办"；
- 每周一自动生成周报发群，不填的人会被看见。

## 12. 待确认事项

在开工前需要客户/你确认：

| # | 问题 | 影响 |
|---|---|---|
| 1 | **现场"没网"具体是哪一种？**（没外网但有 WiFi / 完全无网） | 决定要不要做离线，以及离线做到什么程度 |
| 2 | 车间/办公室有没有一台常开的 Windows 机器？ | 决定内网服务器方案 |
| 3 | 用的人里 iPhone 和安卓各占多少？ | 决定蓝牙/二维码方案是否必须 |
| 4 | "蓝牙同步"是硬需求，还是"没网也能记录、回去能汇总"就够？ | 决定是否 +15–25 人天做原生 App |
| 5 | 要传照片/视频吗？现场照片大概多大、每天多少张？ | 决定存储和同步策略（蓝牙传不了照片） |

| 7 | 有没有企业微信/钉钉？ | 决定提醒通道（机器人最简单） |
| 8 | 导出必须 `.xls` 还是可以 `.xlsx`？ | 决定技术栈（NPOI/Python） |
| 9 | "无损"的验收标准是否认可第 5.1 节的五层定义？ | 决定验收口径 |
| 10 | 项目名用「司南」，还是「信标/墨斗/标点」，或客户指定？ | 决定仓库/界面/文档命名 |
| 11 | 是否需要历史数据（这张表）全量导入？ | 决定导入模板 |
| 12 | 交付后谁维护？ | 决定技术栈偏好（建议 .NET，你能改） |
